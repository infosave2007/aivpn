# Стенд маршрутизации по приложениям

Инструменты проверяют отдельные механизмы ядра и передачи DNS-контекста. Они не включают app-split в клиенте и не подтверждают готовность Windows backend.

Сборщик использует установленное ядро и утилиты, формирует минимальный initramfs и запускает KVM без сетевого устройства. В гостевой ОС создаются два виртуальных пути, cgroup, BPF-программа и локальные TCP/UDP/DNS endpoints. Проверяются ранняя маркировка, исходящие адреса, обратный NAT, запрет обхода при потере VPN-маршрута и управляемый NSS-контекст. Невыбранный процесс при этом сохраняет связь.

Требуются QEMU/KVM, установленное ядро с модулями, Python, C compiler, libbpf headers, nftables, iproute2, systemd-resolved, resolvectl, dbus-daemon, busybox из initcpio и cpio/gzip. Системные пакеты инструменты не устанавливают.

Пример запуска от обычного пользователя:

```bash
python3 tools/app-routing/run_guest.py --output /var/tmp/aivpn-app-lab --kernel VERSION
```

`VERSION` выбирается из `/usr/lib/modules`, где доступны и vmlinuz, и модули. Каталог output должен быть пустым или содержать маркер прежнего запуска этого стенда. После сохранения serial.log, result.json и manifest.json его можно удалить. Проверки границ протокола без KVM запускаются командой `python3 -m unittest discover -s tools/app-routing -p 'test_*.py'`.

На рабочем ПК не нужны sudo и изменение firewall. Сетевые сценарии отказываются запускаться без маркера отдельного guest; вызывать linux_probe.py непосредственно на рабочей системе не следует. Итог проверяется по JSON и маркеру завершения, поскольку успешный выход QEMU сам по себе не означает успех пробы.

Есть проверки ожидаемо неправильных схем: поздняя маркировка сохраняет физический source IP; общий NSS-резолвер не наследует маршрут вызывающего процесса; отказ посредника может включить fallback NSS. Их успешное воспроизведение не является успешной реализацией app-split.

DNS-посредник dns_context.py поддерживает только тестовый A-запрос, не предназначен для установки и не реализует полный протокол systemd-resolved. Положительная проба относится к управляемому mount/NSS-контексту: она не доказывает перехват всех DBus, portal и сторонних resolver API. Кеш, production ACL, восстановление службы и другие типы DNS-запросов требуют отдельных реализаций и проверок.
